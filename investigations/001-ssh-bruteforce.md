> Status: Completed

## Objective

Determine what telemetry was generated when Hydra attempted to brute-force SSH authentication against the Windows domain controller, identify which telemetry was useful for investigation, and identify gaps in the current Wazuh configuration.

## 1. Initial Triage & Isolating Background Noise

Initial triage required separating background Active Directory domain operations from the actual brute-force activity:

    Active Directory Noise:

        Event ID 4624 (Logon Type 3): Recurring Kerberos/NTLM network authentications between domain member computers and the DC (WIN-7HSLQ2235SA$).

        Event ID 4634 / 4672: Routine logoffs and special privilege assignments (SeSecurityPrivilege, SeBackupPrivilege) generated by automated system tasks.

    Attack Artifacts:

        High-frequency bursts of Event ID 4625 (Logon Failure).

        Calling process identifier: C:\Windows\System32\OpenSSH\sshd.exe.

Filtering explicitly by the process name (data.win.eventdata.processName: *sshd.exe*) successfully isolated the adversary's attack stream from background Windows domain noise.

### The Visibility Gap

I noticed that the source ip address and port are not specified. Turns out when OpenSSH on Windows validates incoming user credentials, it hands off authentication locally to the Local Security Authority (LSA) via Advapi / Negotiate. Because the request is processed locally, Windows populates the network fields with dashes (Source Network Address: -).

### Impact

While the SIEM detects that an SSH brute-force attack is occurring, an analyst would be completely blind to the attacker's IP address. No automated blocking, firewall rules, or threat intelligence correlation can be performed based on Event 4625 alone.

## 3. Telemetry Engineering: Subscribing to OpenSSH/Operational

Investigation into native Windows Event Channels revealed that the OpenSSH service maintains an application-level event channel: OpenSSH/Operational.

Querying this channel via PowerShell confirmed that the application layer retains the network metadata that LSA discards:


```powershell
Get-WinEvent -LogName "OpenSSH/Operational" -MaxEvents 2 |
    Format-List TimeCreated, Id, Message
```
Observed output:

```powershell
PS C:\Users\Administrator> Get-WinEvent -LogName "OpenSSH/Operational" -MaxEvents 2 | Format-List TimeCreated, Id, Message


TimeCreated : 11/10/2026 01:00:54
Id          : 4
Message     : sshd: Accepted password for administrator from 10.10.10.30 port 46734 ssh2

TimeCreated : 11/10/2026 01:00:52
Id          : 4
Message     : sshd: Failed password for administrator from 10.10.10.30 port 46734 ssh2

```
### Agent Configuration

By default, the Wazuh Windows Agent only monitors Application, Security, and System. The agent on the Domain Controller was reconfigured to subscribe directly to this channel by adding a new block to C:\Program Files (x86)\ossec-agent\ossec.conf:

```xml
<localfile>
  <location>OpenSSH/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>
```
> Note: An initial attempt to monitor OpenSSH/Admin simultaneously was abandoned because both channels share the same ETW publisher, which created channel handle contention and WARNING: (1958) duplicate file warnings on the agent.

## 4. Infrastructure Obstacles: Clock Drift & Anti-Replay

Even after subscribing to the channel, events initially failed to appear in the Wazuh Dashboard due to two distinct infrastructure obstacles:

### A. Clock Drift

The Windows DC VM had drifted multiple hours (and later multiple days) ahead of the Ubuntu SIEM.

    Dashboard Time Filtering: Events stamped in the future exceeded the default time-picker threshold (now - 15m to now), rendering them invisible on the dashboard.

**Resolution:**

    Configured the Windows DC timezone to W. Central Africa Standard Time (UTC+01:00) to match the SIEM's Africa/Tunis zone.

    Synchronized clocks using Windows Time Service (w32tm /resync /force) and cleared stale agent state counters (Remove-Item "C:\Program Files (x86)\ossec-agent\rids\*" -Force).

### B. The Archive Verification Trap

To verify whether events were physically reaching the manager, logall_json was checked in /var/ossec/etc/ossec.conf. Because logall_json was initially set to no, /var/ossec/logs/archives/archives.json remained silent, giving the false impression that logs were not arriving. Setting <logall_json>yes</logall_json> provided an authoritative baseline proving that raw OpenSSH/Operational events were landing on the SIEM in real time.

> logall_json was set back to no after testing, in order to avoid storage consumption.

## 5. Detection Engineering & The Wazuh Rule Engine Bug

Once the logs were confirmed in archives.json, custom rules were written to alert on the authentication attempts. However, a major Wazuh engine bug was encountered. After many hours of suffering and AI prompting I found out that someone has already highlighted this [issue](https://github.com/wazuh/wazuh/issues/36029) in the Wazuh repo.

Initially, the custom rule was linked to the root Windows EventChannel rule using standard syntax:

```xml
<!-- SILENTLY FAILS IN PRODUCTION -->
<rule id="100001" level="8">
  <if_sid>60000</if_sid>
  <field name="win.system.providerName">OpenSSH</field>
  ...
</rule>
```
    The Bug: In Wazuh v4.x, chaining custom rules to non-standard Windows EventChannels via <if_sid>60000</if_sid> causes the production wazuh-analysisd daemon to silently fail to evaluate child rules.

    The Workaround: Instead of <if_sid>, the rule is changed to use <if_group>windows</if_group>. Because Rule 60000 tags all incoming eventchannel events with the group windows, evaluating via group bypasses the broken if_sid hierarchical pointer while maintaining full Windows tree context.

## 6. Final Detection Ruleset

Deployed to /var/ossec/etc/rules/local_rules.xml on the Wazuh Manager:

```xml
<group name="windows,openssh,">

  <!-- Rule 100001: Successful OpenSSH Connection -->
  <rule id="100001" level="5">
    <if_group>windows</if_group>
    <field name="win.system.providerName">OpenSSH</field>
    <field name="win.system.message">Accepted password</field>
    <description>Windows OpenSSH: Successfull connection($(win.eventdata.payload))</description>
  </rule>

  <!-- Rule 100002: Failed OpenSSH Authentication Attempt -->
  <rule id="100002" level="8">
    <if_group>windows</if_group>
    <field name="win.system.providerName">OpenSSH</field>
    <field name="win.system.message">Failed password</field>
    <description>Windows OpenSSH: $(win.eventdata.payload)</description>
    <mitre>
      <id>T1021.004</id>
      <id>T1110</id>
    </mitre>
  </rule>
  
</group>
```
Result in Wazuh Dashboard

Every brute-force attempt and subsequent successful login now populates directly on the Wazuh Dashboard with the attacker's Source IP and port visible in the alert title:

```text
Windows OpenSSH: Failed password for administrator from 10.10.10.30 port 32790 ssh2
```
### Detection Scope and Limitations

The rules detect individual authentication outcomes:

- **Rule `100001`, level 5:** Successful OpenSSH password authentication.
- **Rule `100002`, level 8:** Failed OpenSSH password authentication.

These rules improve visibility into SSH activity but do not, by themselves, correlate multiple failures and a subsequent success into a single brute-force incident. That correlation is a potential future improvement.

The MITRE ATT&CK mappings provide technique context; they do not independently prove that a particular event represents a confirmed attack or lateral movement.

## 7. Attack Timeline & End-to-End Reconstruction

The most direct attack evidence is the Windows OpenSSH telemetry surfaced by the custom rules: seven failed-password alerts and one accepted-password alert.

### Interpretation
1. **Strongest evidence — OpenSSH Event ID `4`:** all eight SSH outcome messages identify `administrator` and the same source IP, `10.10.10.30`. The custom rules make the outcome explicit: Rule `100002` marks failed passwords at level 8 and Rule `100001` marks an accepted password at level 5.
2. **Outcome — authentication succeeded:** the `Accepted password` message confirms that the SSH server accepted credentials for `administrator` from `10.10.10.30` on source port `53374`. It does not by itself show what happened after login.
3. **Do not force success to the end:** the success and one failure share the same millisecond timestamp, and additional failed events have later timestamps. The log order is not the wordlist order. The source ports also cannot identify which password-file entry was accepted.
4. **Windows Security corroboration — useful, but not fully correlated in this export:** the seven Rule `60122` failure alerts occur after the eight OpenSSH messages in the displayed sequence. They dont offer much information.

## 8. Key Takeaways & Lessons Learned

The first major finding was that the availability of an authentication alert does not guarantee that it contains the information an analyst needs.

Windows Security Event ID 4625 exposed failed authentication associated with sshd.exe, but the observed records did not contain the remote source IP address or port.

**Lesson learned:** For service-specific attacks, collect telemetry from the service itself instead of relying exclusively on generic operating-system security events.

The initial Wazuh dashboard contained numerous authentication events generated by routine domain operations, including Kerberos and NTLM activity, machine-account authentication, logoffs, and privileged logons.

Filtering by relevant attributes, particularly the calling process sshd.exe, helped narrow the investigation to events associated with the target service.

**Lesson learned:** Effective triage requires contextual filtering. Understand which processes, accounts, event IDs, and systems are relevant before interpreting an alert as malicious.

The OpenSSH events did not immediately appear as expected in the dashboard after the agent configuration was updated.
The investigation highlighted several troubleshooting considerations:
- Time synchronization: The Windows DC and SIEM manager need consistent clocks for reliable event ordering.
- Agent collection: The intended Windows event channel must be configured and collected correctly.
- Manager ingestion: Verify that events reach the manager rather than assuming that a running agent guarantees successful ingestion.
- Archive configuration: The absence of records in archives.json is not proof that the manager received no events when raw-event archiving is disabled.
- Dashboard filtering: Events can be ingested but remain outside the selected time range.
**Lesson learned:** Validate telemetry at each stage: source host, agent, manager, rule processing, and dashboard. This helps distinguish collection failures from ingestion, detection, and visualization problems.
